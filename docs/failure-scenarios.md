# Failure Scenarios (Phases 1 – 7)

This matrix documents the explicit failure handling mechanisms implemented and tested across the system through Phase 7. Each scenario outlines the architectural failure mode, observed system behavior, and automated test coverage.

| # | Scenario | Failure Mode & Handling | Observed Behavior | Test Suite Coverage |
|---|---|---|---|---|
| 1 | **Missing S3 Object on Complete** | Client calls `POST /uploads/:id/complete` after failing to PUT bytes to S3. | Server calls `HeadObject`. Detects missing key, transitions status to `FAILED` with `failureReason: "S3 object not found at completion time"`. Returns `422 Unprocessable Entity`. Never marked `COMPLETED`. | `uploads.presigned.test.js`, `multipartUpload.test.js` |
| 2 | **Duplicate Completion Calls** | Client calls `POST /uploads/:id/complete` on an already-`COMPLETED` record. | Checks status; returns existing completed metadata directly (`200 OK`) without triggering duplicate state transitions or duplicate SQS events. | `uploadStateMachine.test.js`, `uploads.presigned.test.js` |
| 3 | **Completion from Illegal Status** | Client calls complete while file is in `INITIATED` or `FAILED`. | Throws `ValidationError` (`400 Bad Request`); does not call S3 `HeadObject` or update DynamoDB. | `uploadStateMachine.test.js` |
| 4 | **Illegal State Machine Jumps** | Code attempts illegal jump (e.g., `INITIATED -> COMPLETED` directly). | `assertValidTransition` throws `InvalidStateTransitionError` (`400`); transaction aborted before any DynamoDB update. | `uploadStateMachine.test.js` |
| 5 | **Idempotent File Deletion** | Client calls `DELETE /files/:id` on an already-deleted or nonexistent file. | Scans DynamoDB for file; returns `200 { deleted: true, alreadyDeleted: true }` without error. | `uploads.presigned.test.js`, `files.service.js` |
| 6 | **Partial Delete Failure (S3 succeeded, DynamoDB failed)** | S3 `deleteObject` succeeds, but subsequent DynamoDB `deleteItem` fails. | Error logged prominently with category `DYNAMODB_DELETE_FAILED_AFTER_S3_DELETE`. Caller receives `502 Upstream Error`. Orphaned metadata row is repaired by Phase 7 Reconciliation Case A. | `files.service.js`, `reconciliation.processor.js` |
| 7 | **Unauthorized Access / Cross-Tenant Scoping** | User attempts `GET`, `download`, or `DELETE` on another user's file. | Partition key is always derived from authenticated JWT (`USER#<userId>`). Returns `404 Not Found` (never confirms file existence to unauthorized callers). | `files.ownership.test.js`, `filesRepository.test.js` |
| 8 | **Download of Incomplete/Failed File** | Client requests download for a file in `INITIATED`, `UPLOADING`, `COMPLETING`, or `FAILED`. | Gated by `status === 'COMPLETED'`. Returns `409 Conflict` explaining download is unavailable for current status. | `uploads.presigned.test.js` |
| 9 | **Missing or Expired JWT** | Unauthenticated request sent to protected endpoints. | `authGuard` middleware validates signature & expiration; returns `401 Authentication Error`. | `auth.flow.test.js` |
| 10 | **Multipart Incomplete / Missing Part** | Client completes multipart upload with missing or invalid part numbers/ETags. | S3 `CompleteMultipartUpload` or subsequent `HeadObject` fails; status transitions to `FAILED` with `422`. | `multipartUpload.test.js` |
| 11 | **User-Aborted Multipart Upload** | Client calls `POST /uploads/:id/multipart/abort`. | S3 `AbortMultipartUpload` frees stored part buffers in S3; record marked `FAILED` with `failureReason: "Aborted by user"`. | `multipartUpload.test.js` |
| 12 | **Abandoned Upload Cleanup** | Uploads stuck in `UPLOADING` past retention cutoff (24h) or `COMPLETING` past cutoff. | Periodic cleanup worker (`cleanup.processor.js`) issues S3 `AbortMultipartUpload` and marks DynamoDB records `FAILED`. | `cleanup.processor.test.js` |
| 13 | **API Instance Crash Mid-Traffic** | One of 3 API replicas (`api-2`) stops responding mid-traffic. | Nginx load balancer detects failure (`max_fails=3 fail_timeout=30s`) and fails over transparently via `proxy_next_upstream`. 100% of requests succeed. | `crash-tolerance.sh`, `crash-tolerance.md` |
| 14 | **S3 Client Presign / Network Timeout** | Outbound S3 request times out during upload initiation. | S3 client enforces `connectionTimeout` (3s) and `socketTimeout` (30s). Throws upstream error, transitions record to `FAILED`, and logs `S3_PRESIGN_FAILED`. | `s3Timeout.test.js` |
| 15 | **DynamoDB Write Failure After S3 Action** | DynamoDB status update fails after S3 presigned URL generation. | Error logged with category `DYNAMODB_UPDATE_FAILED_AFTER_S3_PRESIGN`. Caller receives error; reconciliation worker detects unconfirmed records. | `dynamoPostS3.test.js` |
| 16 | **Concurrent Requests with Same Idempotency Key** | Two concurrent identical requests sent with the same `Idempotency-Key`. | DynamoDB conditional put (`attribute_not_exists(PK)`) acquires lock. First request sets `IN_PROGRESS`; second request receives `409 Conflict`. | `idempotency.concurrent.test.js` |
| 17 | **Idempotency Key Payload Mismatch** | Client reuses an `Idempotency-Key` with a different request payload. | Request body SHA-256 hash does not match stored `requestHash`. Server rejects with `422 Unprocessable Entity`. | `idempotency.middleware.js` |
| 18 | **Validation Errors Bypassing Retry** | Client submits invalid payload (oversized file, illegal contentType). | Throws `ValidationError` immediately. Bypasses AWS SDK retry loop and returns `400 Bad Request` without redundant retries. | `retryNotRetried.test.js` |
| 19 | **Failed Upload Resumption & Retry** | Client calls `POST /files/:id/retry` on a `FAILED` upload. | Re-issues presigned URL and resets state to `UPLOADING` without creating duplicate database records or ghost S3 keys. | `s3Timeout.test.js`, `multipartUpload.test.js` |
| 20 | **Worker Crash Mid-Message Processing** | Worker process killed or throws unhandled error before SQS ack. | `DeleteMessage` is never called. SQS visibility timeout (300s) elapses, and message is re-delivered to another worker replica. | `consumer.js`, `workerCrash.test.js` |
| 21 | **Poison Pill Message in SQS** | Message continually fails processing across all retries. | SQS tracks `ApproximateReceiveCount`. After `maxReceiveCount=5`, SQS moves message to `file-processing-dlq`. | `dlqRouting.test.js`, `inspect-dlq.js` |
| 22 | **Reconciliation Case A (DB exists, S3 missing)** | Item stuck in `UPLOADING`/`COMPLETING` or marked `COMPLETED` with missing S3 object. | Worker queries S3 via `HeadObject`. If missing (404), marks DynamoDB record as `FAILED` with `failureReason: "reconciliation: object missing"`. | `reconciliation.processor.test.js` |
| 23 | **Reconciliation Case B (S3 exists, DB missing)** | S3 object has no active DynamoDB record older than orphan grace period (60m). | Worker sweeps bucket via `ListObjectsV2`, checks DynamoDB ownership, verifies no active deduplication references, and deletes the orphan S3 object. | `reconciliation.processor.test.js` |
| 24 | **Deduplicated File Deletion Race** | User deletes an alias file pointing to a shared canonical S3 object. | Decrements canonical `refCount`. Preserves S3 object so other referencing files remain downloadable. S3 object deleted only on last reference removal. | `dedup.delete.test.js`, `dedup.checksum.test.js` |
| 25 | **Shared-State Rate Limit Burst** | Client sends requests exceeding quota across multiple API replicas. | Redis shared counter atomically tracks requests. When limit exceeded, returns `429 Too Many Requests` with `Retry-After` header. | `rateLimiter.test.js`, `rateLimiter.integration.test.js` |
